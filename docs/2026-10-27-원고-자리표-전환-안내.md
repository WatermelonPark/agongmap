## 2. 쓸 수 있는 자리표 — 키와 실제 출력

값은 문장 안에 넣고, 표는 그 자리에 블록으로 들어간다. **단위는 자리표에 이미 들어 있다** — 뒤에
'세대'·'%' 를 또 쓰면 '3,962세대세대' 가 된다(첫 19편에서 44곳이 그랬다).

### 값 (`{{v:…}}`)

| 자리표 | 나오는 글자 |
|---|---|
| `{{v:moveins:인천:2027}}` | `26,935세대` |
| `{{v:moveins:부천:2027}}` | `3,962세대` (도시도 같은 키) |
| `{{v:supply:인천}}` | `8,033세대 여유(1년 적정물량의 0.3배)` |
| `{{v:weekly:인천}}` | `+0.02%` |
| `{{v:weekly:분당구}}` | `+0.53%` (시군구도 된다) |
| `{{v:stats:미분양:인천}}` | `3,729호` |
| `{{v:share:평택:2027}}` | `224%` (그 해 물량 ÷ 한 해 적정 입주량) |
| `{{v:streak:분당구}}` | `84주 연속 상승(10월 19일 조사)` |
| `{{v:streak:분당구:전세}}` | `6주 연속 상승(10월 19일 조사)` |
| `{{v:need:부천}}` | `6,030세대` (한 해 적정 입주량) |
| `{{v:pop:부천}}` | `753,731명(2026년 9월 주민등록)` |
| `{{v:peak:부천}}` | `2032년 3월 1,859세대` (가장 몰리는 달) |
| `{{v:peak:부천:2027}}` | `2027년 11월 1,640세대` (그 해 안에서) |

### 표 (`{{table:…}}`)

| 자리표 | 머리 · 행수 · 첫 줄 |
|---|---|
| `{{table:moveins:인천}}` | 연도·세대·구분 / 13행 / `2017 · 16,366 · 실적` |
| `{{table:moveins:인천:2027}}` | 분기·세대·구분 / 5행 / `2027Q1 · 6,880 · 예정` |
| `{{table:moveins:부천}}` | 연도·세대·적정 대비 / 5행 / `2026 · 1,859 · 31%` |
| `{{table:moveins:부천:2027}}` | 지역·세대 / 4행 / `오정구 · 2,268` (도시는 그 해 **구별**) |
| `{{table:supply:인천}}` | 항목·값 / 5행 / `분기 적정물량 · 5,800호` |
| `{{table:stats:인허가:인천}}` | 기간·인허가(호, 연내 누계) / 12행 / `2025.09 · 15,684` |
| `{{table:weekly:인천}}` | 조사 기준일·매매·전세 / 8행 / `2026-08-31 · +0.01% · +0.19%` |
| `{{table:weekly:고양}}` | 지역·매매·전세 / 3행 / `고양 덕양구 · +0.10% · +0.10%` (**구별 한 줄씩**) |
| `{{table:complexes:부천:2027}}` | 입주 예정·단지·구·세대 / 16행 / `2027-01 · 부천아테라자이(부천괴안지구 B-2) · 소사구 · 200` |

`stats` 의 계열은 인허가·미분양·전세가율·준공·착공이다. 지역 이름은 화면 이름(`광주·전남`)과 내부 키
(`전남광주`) 둘 다 받는다. 시군구 이름이 겹치면 `고양 덕양구` 처럼 구까지 적는다. 모르는 자리표와 없는
지역은 실패로 처리한다 — 빈 표가 나가지 않는다.

## 3. 원고 19편의 형식 오류

**형식 오류는 0건이다**(`python tools/content_check.py` 전수 통과). 프런트매터·자리표·날짜·slug 모두 규약에
맞았다. 다만 두 가지를 개발이 손봤다.

1. **단위 중복 44곳** — `{{v:moveins:…}}세대` 가 '3,962세대세대' 로 나오던 자리에서 뒤의 '세대' 를 뺐다.
   원고 내용은 그대로다. 앞으로 숫자 자리표 뒤에 단위를 덧붙이지 않는다.
2. **요약과 FAQ 의 자리표가 치환되지 않던 것** — 생성기가 본문만 채우고 있어서 페이지의 요약·OG·JSON-LD
   설명·FAQ 답과 `feed.xml`·`llms.txt` 에 `{{v:…}}` 가 그대로 나갈 상태였다. 치환을 한 입구로 모아 고쳤다.
   원고는 손대지 않아도 된다.

요약 길이 상한은 180자로 올렸다(요청서는 40~60자였으나 실제 원고가 숫자와 출처를 담아 100자를 넘었다).

## 4. 자리표로 바꿀 수 있는 손 숫자 (세션 몫)

형식 오류는 아니지만, 지금 손으로 적힌 숫자는 다음 수집에서 데이터와 멀어진다. 확인한 값은 모두
데이터와 일치했다(부천 2032년 3월 1,859세대 포함) — 틀린 것이 아니라 늙는 것이 문제다.

도시 편은 네 가지가 글마다 되풀이된다.

GTX 편 7편과 단지 편 3편은 적정 대비 비율이 글마다 4~6개씩 손으로 적혀 있다. 그 비율이 '그 해 물량 ÷
한 해 적정 입주량' 이면 `{{v:share:도시:연도}}` 로 바꿀 수 있다. 분양가 대비처럼 다른 뜻의 비율과 단지
규모(1,842세대 같은 값)는 그대로 둔다 — 단지 하나의 세대수는 자리표가 없고, 단지 목록 표는
`{{table:complexes:도시:연도}}` 로 받는다.

가장 몰리는 달을 말하는 문장은 `{{v:peak:도시}}` 로 숫자만 받고 단지 이름은 원고가 쓴다. 원천의 이름이
'…외가로주택정비사업' 처럼 길어 문장에 그대로 들어가지 않는다.

## 5. 도시(시군구) 숫자는 어디서 오나

승인된 1번 안대로 구현했다. 배치가 `content/` 원고의 `region` 과 본문 자리표에서 도시를 읽어
`tools/city_movein.py` 로 수집하고 `tools/data/city_moveins.json` 에 쓴다. **손 목록이 없으므로 새 도시를
쓰면 다음 배치에서 자동으로 들어온다.**

- 수집은 키가 있는 잡에서 돈다(청약홈·한국부동산원·KOSIS). 실패하면 옛 파일을 그대로 두고 그 글의 숫자만
  한 회차 묵는다 — 배치를 세우지 않는다.
- 지금 담긴 도시 13곳(2026-10 기준, 목록 끝 2028-06): 고양·구미·김포·부천·성남·수원·용인·의정부·창원·
  춘천·파주·평택·화성.
- 적정 입주량 산식의 정본은 `tools/movein_need.py`(인구 ÷ 2.5 × 2%, 2026-09-30 대표 결정)다. 도시 글
  생성기와 수집기가 같은 파일을 읽는다.

## 6. 원고를 올리는 방법이 바뀌었다

`content/` 를 푸시하면 발행 워크플로가 **5분 안에** 글을 굽는다(검사 → 생성 → 시험 → 커밋). 다음 배치를
기다리지 않는다(대표 결정 10-26 ①). 숫자를 새 데이터로 다시 채우는 일은 매일 배치가 한다.

올리기 전에 이것을 돌리면 어긋난 자리를 파일·줄 번호로 알려 준다.

```bash
python tools/content_check.py
```

쓸 수 있는 자리표 전체와 프런트매터 규약은 [content/README.md](../content/README.md) 에 있다.
